# Ruleset reduction

## Goal

Create a substantially smaller new repository practice-set version containing only agreed essentials and important practices. Unlike version 4's shorter entry point, this review may explicitly retire or make obligations optional; it must not merely move the same mandatory reading elsewhere.

## Scope

- Review repository guidance, detailed practices, current and retired principle entries, practice/process documents, both custom agents and all five repository skills.
- Review each item with the user; consolidate duplicates rather than counting repeated wording as separate decisions.
- User/profile/plugin customizations may be identified as dependencies, but changing them requires separate scope approval. Platform/runtime requirements are outside the repository practice-set scope and cannot be removed by this review.
- Preserve previous versions and source history. Current rules remain active until the replacement is explicitly approved.

## Agreed classification

- Must: essential to the new ruleset.
- Should: important but not essential.
- Could: optional/on-demand.
- Won't: excluded from this new version, not deleted from history.

Classification alone does not decide placement or enforcement. Record whether each retained item is always-on guidance, an on-demand process/skill/agent, or reference-only. Dependencies and conflicting decisions must be surfaced before implementation.

## Steps

1. Establish a complete, deduplicated inventory and baseline size. Distinguish active obligations, examples, historical entries and supporting references.
2. Agree the smallest Typed JSON decision ledger and its existing/new interface before adopting a structured representation. Keep this narrative workflow as the resumable checkpoint, not a second decision authority.
3. Review each item with the user using MoSCoW. Record the decision, rationale, dependencies, disposition and any wording to retain. Unreviewed items remain undecided.
4. Agree a measurable size budget for always-on guidance and mandatory referenced material; do not silently invent a threshold.
5. Draft the reduced set from approved decisions and validate realistic tasks: coding/test repair, a same-task refinement, metrics upkeep and a requested commit.
6. Verify coverage of the inventory, links, loading scope and removed obligations. Obtain approval before replacing current guidance.
7. Follow existing versioning policy: commit actual practice changes only on request, then register the next sequential version pinned to that committed content in a follow-up commit. Do not invent activation dates or a source commit.
